Osprey Document Bench

Python PostgreSQL OpenAI API n8n Supabase Google Drive FastAPI

Care agencies, construction firms and staffing agencies keep a folder for every person: IDs, contracts, certificates, care plans. The costly mistake is not an incomplete folder — it is a folder everyone believed was complete. Osprey reads every document in your Google Drive folders, recognises each one by what is on the page rather than what the file is called, and tells you, person by person, what is missing, what has expired, what is about to, and what belongs to someone else. And like Kestrel, it is measured: two batches of folders with problems planted and recorded in advance — the second generated after the system was frozen.

→Not one incomplete folder reported as complete, in either batch. Whatever the system is unsure of goes to a person.
→The model sees the page, never the file name. A file called “BGCHECK” that is really a contract gets caught, not believed.
→You set the required documents and validity periods, not the system. Another industry means new rows in a rules table, not new code.
→Dates exact to the day — including documents that print only an issue date (“valid for 3 years”). Warnings at 90, 60 and 30 days.
→A Google Sheets report per person, and a review screen where a person sees the same page the model saw.
→Read-only: nothing in Drive is renamed or moved. The system suggests; people decide.

The folders are synthetic and every name is fictional. The second batch included 13 document layouts the system had never seen: 109 of 110 — the one left over went to a person, not missed.

Review screen · measured against a known answer
Finance / Accounts Payable
Kestrel Invoice Bench
MEASURED
94/98
planted errors found and named correctly
Python PostgreSQL OpenAI API n8n Supabase FastAPI

Most invoice checking systems tell you how many discrepancies they found. None tell you how many they missed — and a missed invoice leaves no trace. So this one was built backwards: first a batch of 260 invoices with 98 errors planted and recorded on purpose, then the pipeline that gets measured against that record. Extraction, arithmetic, contract pricing, reconciliation and a human review screen — with a number attached to every claim.

→Ground truth isolated by database roles — the pipeline cannot read the answer key, and that is enforced by Postgres, not by good intentions
→The model reads, the code counts — not one arithmetic operation or price comparison is delegated to the LLM, so a run repeats identically
→Prices looked up by delivery date, not invoice date — an April invoice for a March delivery is checked against March’s contract
→Eight kinds of discrepancy: price above contract, stale price list, missing contract discount, wrong VAT rate, duplicate invoice, and more
→A review screen, not an alert list — the invoice beside its findings, one decision per finding, every decision logged and reversible
→The system never rewrites a supplier’s invoice — it shows the discrepancy to a person, who decides whether to ask the supplier for a corrected one, because rewriting someone else’s document destroys the audit trail

The invoices are synthetic. That is what makes the number possible: with real documents nobody knows the right answer in advance — if they did, the checking would be unnecessary.
